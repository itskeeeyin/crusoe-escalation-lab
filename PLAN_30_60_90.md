# 30 / 60 / 90-day plan

A personal plan for the first 90 days as a Senior Escalation Manager at Crusoe. It is grounded in public Crusoe products and in how I have run escalations before. It is not a Crusoe-internal policy, and it does not describe confidential work from prior roles or quote any confidential deck.

Public product surfaces this plan assumes, from current docs:

- Intelligence Foundry / Serverless Inference, including the OpenAI-compatible API, rate limits, and Self-Serve Deployments: https://docs.crusoe.ai/quickstart/getting-started-with-serverless-inference/ and https://docs.crusoe.ai/serverless-inference/rate-limits/
- Infrastructure Cloud: GPU and CPU VMs, storage, networking, and orchestration: https://docs.crusoe.ai/infrastructure-cloud/overview.md
- Crusoe Managed Kubernetes (CMK): https://docs.crusoe.ai/orchestration/cmk/overview.md
- Crusoe Managed Slurm: https://docs.crusoe.ai/orchestration/slurm/overview.md
- Storage: ephemeral, persistent, and shared disks, plus S3-compatible object storage: https://docs.crusoe.ai/storage/disks/overview.md and https://docs.crusoe.ai/storage/object-storage/overview/

Prior work this plan borrows habits from, not case files: escalation management at ServiceNow, API and gateway issues at Kong, cluster orchestration at Mesosphere, and enterprise infrastructure operations at VMware.

## Proposed severity matrix

This matrix is a practice starting point, not Crusoe's published policy. Adjust it to match whatever severity and comms rules Crusoe already uses.

| Severity | Customer impact | First response | Update cadence | Stay engaged until |
| --- | --- | --- | --- | --- |
| P0 | Production down or data at risk across a region or a core product (inference API failing for many customers, CMK control plane unavailable, widespread VM or storage loss) | Minutes | Every 1 hour, or on each material change | Mitigation or a documented workaround is in place |
| P1 | Major production degradation or a silent failure that breaks a customer workflow (blank completions on HTTP 200, a cluster that cannot schedule GPUs, shared `/home` unavailable on Managed Slurm) | Same day, quickly | Every 4 hours | Mitigation confirmed by the customer, or a clear owner and next time |
| P2 | Partial impact, a workaround exists, or a non-production environment is blocked | Next business day | Daily | Fix or accepted workaround |
| P3 | Questions, docs gaps, feature confusion, or a single-client config issue | Queue order | As committed | Answered, or converted to a feedback ticket |

Comms rule: if you said "next update in 4 hours," send the update even if the only news is "we are still working, nothing has changed." Missed cadence is its own failure.

## Days 1–30: learn the surfaces and make the path obvious

Goal: be useful on an incoming P1 without pretending to know internals that are not in the docs or in the ticket.

- Walk the public product map above, and keep a one-page "where this ticket lives" note: Intelligence Foundry vs Infrastructure Cloud, Serverless vs Self-Serve Deployments, CMK vs Managed Slurm vs a single VM, disk vs object storage.
- Keep using this lab. The empty-reply case, the 401/404/400 shapes, and the rate-limit headers are already recorded. Add a healthcheck to anything I touch so HTTP-only monitors are not the only signal.
- Sit with support, TAM, and engineering on live escalations. Goal is to learn the existing path, not to invent a parallel one.
- Write the first-pass playbook for Serverless Inference: what the customer sees, which fields to collect (`model`, `status`, `content`, `finish_reason`, `usage`, rate-limit headers, request ID), when it is a client config issue, and when to escalate.
- Agree the severity and comms cadence with the people who already own the queue. If Crusoe already has a matrix, use it. If not, propose the table above.
- Start an engineering-and-docs feedback log in the same shape as `VOICE_OF_CUSTOMER.md`: one ticket, one source, one suggested fix. No drive-by opinions.

Exit for day 30: I can run a P1 on Serverless Inference from first customer sentence to a 4-hour update without getting the product family wrong, and I have a written path into engineering.

## Days 31–60: playbooks for the rest of the stack, and a closed loop

Goal: the same quality of triage on CMK, VMs, Slurm, and storage, and a visible place for patterns to land.

- Add playbooks for:
  - CMK: control plane vs node pool vs add-on (GPU operator, network operator, CSI) vs AutoClusters remediation. Public overview: https://docs.crusoe.ai/orchestration/cmk/overview.md
  - GPU VMs: instance type and interconnect, on-demand vs spot vs reserved, "the VM is up but the job cannot see the GPU or the fabric."
  - Managed Slurm: queue vs node set capacity vs login node vs shared `/home`. Public overview: https://docs.crusoe.ai/orchestration/slurm/overview.md
  - Storage: ephemeral data loss vs persistent disk attach/detach vs shared disk NFS vs regional object storage and separate S3 keys. Public overviews linked above.
- Stand up the feedback loop: every repeating incident or docs mismatch becomes a ticket with evidence, severity, and a suggested owner (docs, inference, orchestration, storage). Review it with engineering on a fixed cadence, not in the heat of a P0.
- Publish comms templates for accept, investigating, workaround, mitigated, and close, for P0 (hourly) and P1 (every 4 hours). Keep them short and specific. Examples are already in this lab and in the hypothetical postmortem.
- Define a small metrics set and start measuring it, even if the first month's data is messy. See the metrics section below.
- Practice one incident review using a clearly labelled hypothetical, like `postmortems/P1-blank-agent-responses.md`, so the format is familiar before it is needed on a real case.

Exit for day 60: each public product family has a triage path, a comms template, and a way for a repeating issue to reach the team that can change the product or the docs.

## Days 61–90: tighten the system

Goal: reduce time-to-mitigation, and make the playbooks the default, not a side document.

- Review the first 60 days of escalations: where time was lost (wrong product family, missing fields, waiting on a comms cycle, docs vs product mismatch). Fix the playbook, not just the ticket.
- Agree a weekly or biweekly feedback review with engineering and docs. The VoC tickets from this lab are the kind of input that should show up there: silent HTTP 200 failures, parameter differences across models, signup docs that disagree.
- Run a tabletop on a cross-product incident (for example: a training job on Managed Slurm is stuck, and the cause might be node set capacity, shared disk, or the object-storage path for checkpoints). The point is a clean handoff, not a theatrical exercise.
- Teach the inference empty-content check to anyone who owns a customer monitor. The healthcheck in this repo is a starting example, not a production mandate.
- Publish v1 of the escalation playbook and the severity matrix, with owners and review dates.

Exit for day 90: a new escalations teammate can pick up a P1, find the playbook, send a cadence-correct customer update, and know when to escalate to engineering.

## Escalation playbook, in one page

1. Classify the product family and the severity. If it is unclear, say so, and start at P1 rather than under-classifying a production issue.
2. Collect evidence, not vibes. For inference: status, body, headers, model ID, timestamps, and a sample request that can be reproduced with a non-production key. For infra: resource IDs, region, instance or cluster type, and the last change.
3. Reproduce, or show that you cannot. This lab exists so the inference shapes are already known.
4. Separate client-config, customer-quota, and platform issues. A typo'd model ID, a missing key, a malformed body, a low `max_tokens` on a reasoning model, or a 429 that matches remaining quota stays with the customer workaround. A listed model ID returning 404, a known-good key returning 401, a valid payload returning 400, empty replies after a generous cap and lower reasoning, 429s well under the header limits, or 503s after backoff goes to engineering.
5. Mitigate first. Give the customer something they can do now. Then chase the durable fix.
6. Communicate on the cadence you promised. Name the next update time.
7. Close with the cause, the workaround, and a prevention item. If the cause is a docs gap, file it.

## Comms templates

**P1 accepted:**

> We're investigating [symptom] affecting [product / model / cluster]. We have not declared a broader outage. We're collecting [specific fields]. Next update in 4 hours, or sooner if we have a workaround or a fix.

**P1 investigating, with a workaround:**

> Early evidence points to [cause shape], not [ruled-out cause]. Workaround: [exact steps]. Next update in 4 hours, or sooner if you confirm the workaround on your side.

**P1 mitigated:**

> [Symptom] is consistent with [cause]. Please keep [workaround] in place. We'll watch [signal] and follow up on [docs / monitor / product] changes. If it recurs after [the thing that should have fixed it], we will reopen and escalate to engineering.

**P0** uses the same structure, hourly.

## Metrics

Start with a short list, and only add more if a decision needs it:

- Time to first customer response, by severity
- Time to mitigation (workaround or fix in the customer's hands)
- Cadence kept: promised 4-hour (or hourly) updates actually sent
- Percent of tickets re-classified after first contact (a proxy for "we got the product family or severity wrong")
- Feedback tickets opened from incidents, and feedback tickets closed with a docs or product change
- Recurrence of the same symptom after a closed P1

Do not invent baselines before there is data. The first 30 days are for instrumenting; the next 60 are for looking at the numbers.

## How this uses earlier experience, without importing confidential work

- ServiceNow escalation management: keep a severity and comms cadence, and treat a missed update as a break in the process.
- Kong: API-shaped failures are often in the request, the auth header, or the status the client ignored. The inference lab is the same habit against an OpenAI-compatible API.
- Mesosphere: when a distributed job fails, ask which layer first (scheduler, node, network, storage) before escalating every team at once. That maps cleanly onto CMK, Managed Slurm, and VM fabric tickets.
- VMware: enterprise customers want a clear owner, a next update time, and a mitigation they can take without waiting for a deep root-cause write-up.
